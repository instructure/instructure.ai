# Copilot Studio and Superhuman Go: connecting a static-credential OAuth MCP server

Date checked: 2026-10-17. Method: WebFetch/WebSearch. help.superhuman.com returned HTTP 403 to every fetch, so Superhuman help-center articles were NOT read (only search-result snippets and coda.io / superhuman.com/go pages). ## A. Microsoft Copilot Studio

### A0. Modes

- Personal vs enterprise: Copilot Studio has no "personal" install mode for MCP. A maker adds the MCP server to an agent; end users then sign in (per-user connection). The Canvas key is the same private key either way. For the repo, "enterprise" (maker/admin configured) is the only meaningful mode. Source below says nothing about a separate personal flow.
- Transport: Streamable HTTP only. SSE was dropped after August 2025.
- Source: https://learn.microsoft.com/en-us/microsoft-copilot-studio/mcp-add-existing-server-to-agent (ms.date 2026-05-28, updated_at 2026-10-15). Checked 2026-10-17.

### A1. Maker steps: add MCP server with manual OAuth (MCP onboarding wizard, "recommended" method)

Roles: a maker with permission to create/edit agents in a Copilot Studio environment. The page doesn't name a specific role beyond that. If the connector is edited afterward, that happens in Power Apps / Power Automate under Custom connectors.

1. Open the agent, go to the **Tools** page. SCREENSHOT: copilot_tools_page — agent Tools page with "Add a tool" button visible.
2. Select **Add a tool**, then **New tool**. SCREENSHOT: copilot_new_tool_menu — Add a tool panel with "New tool" option.
3. Select **Model Context Protocol**; the MCP onboarding wizard opens. (Sibling option on the same screen: **Custom connector**, which is Option 2, an OpenAPI import via Power Apps.) SCREENSHOT: copilot_mcp_wizard_blank — wizard with Server name, Server description, Server URL, authentication type.
4. Fill **Server name**, **Server description** (the orchestrator uses it to decide when to call the server), **Server URL**. SCREENSHOT: copilot_mcp_wizard_basics — three basic fields filled in.
5. Authentication type: options are **None**, **API key**, **OAuth 2.0**. Choose **OAuth 2.0**. Then **Type**: **Dynamic discovery**, **Dynamic**, **Manual**. Choose **Manual**. SCREENSHOT: copilot_oauth_type_manual — OAuth 2.0 with Type = Manual selected.
6. Manual fields (all enterable by hand): **Client ID**, **Client secret**, **Authorization URL**, **Token URL template**, **Refresh URL**, **Scopes** (optional, space-separated list). SCREENSHOT: copilot_manual_oauth_fields — all six fields filled (secret masked).
7. Select **Create**. A **callback URL** appears (the docs call it "callback URL"; this is the redirect URI). Copy it and register it on the identity provider app (the Canvas developer key's redirect URIs). SCREENSHOT: copilot_callback_url — callback URL shown after Create, with copy control.
8. Select **Next**. The **Add tool** dialog opens. SCREENSHOT: copilot_add_tool_dialog — Add tool dialog with "Create a new connection".
9. Select **Create a new connection** (or reuse an existing connection), sign in to Canvas when prompted, then **Add to agent**. SCREENSHOT: copilot_canvas_signin — Canvas OAuth consent popup. SCREENSHOT: copilot_tool_added — MCP tool listed under agent Tools.

Redirect URI behavior: generated by Copilot Studio after **Create** (per server); no fixed value is published on the page. Unlike Dynamic, where the callback "might" appear, Manual always shows it. The doc does not state whether the value is stable across servers/environments; ask Microsoft or verify per tenant. The wizard is the only place the value was documented as appearing; the page doesn't describe re-viewing it later.
Client secret: a related Power Apps connector guide (search snippet, not fetched) says the secret isn't persisted and must be re-entered when editing the connector. Not confirmed on the fetched page.

### A3. Governance (admin)

- Source: https://learn.microsoft.com/en-us/microsoft-copilot-studio/admin-data-loss-prevention (ms.date 2026-10-01, updated 2026-10-15). Checked 2026-10-17.
- Access to MCP servers relies on Power Platform connectors, so data policies that regulate connectors also regulate the MCP server and its tools. "Blocking Power Platform connectors also blocks access to tools in connected MCP servers."
- Admin prerequisite: tenant admin or Environment Admin role.
- PPAC path: https://admin.powerplatform.microsoft.com/ -> sidebar **Security** -> **Data and privacy** -> **Data policy** -> **New Policy** (or select existing, **Edit Policy**) -> **Next** -> **Add an environment** (**Add to policy**) -> **Next** -> **Assign connectors** (search; "⋮" menu; **Block**, or Business / Non-business groups) -> **Next** -> **Define scope** (**Add all environments** / **Add multiple environments** / **Exclude certain environments**) -> **Create policy** / **Update policy**.
  SCREENSHOT: ppac_data_policy_list — PPAC Security > Data and privacy > Data policy list.
  SCREENSHOT: ppac_assign_connectors — Assign connectors page with custom connector in Business group.
- Connectors in one policy must be in the same data group to share data (Business / Non-business / Blocked). Custom connectors default to the default group (often Non-business); the Canvas MCP connector and other agent connectors must be classified consistently or the Publish button is disabled and an error banner with **Details** appears (Channels page -> expand error -> **Download**).
- Real-time enforcement; blocked connectors appear disabled in the maker UI.
- Teams/M365 channel is itself a governed connector: **Microsoft Teams + Microsoft 365 Channel in Copilot Studio**.
- The page does not mention endpoint filtering for MCP specifically. It does not list a named MCP connector entry; the custom connector created by the wizard appears under custom connectors in PPAC (inferred, not stated).

### A4. Publishing to Teams / Microsoft 365 Copilot

- Source: https://learn.microsoft.com/en-us/microsoft-copilot-studio/publication-add-bot-to-microsoft-teams (ms.date 2026-08-17, updated 2026-10-03), and https://learn.microsoft.com/en-us/microsoft-copilot-studio/configuration-end-user-authentication (ms.date 2026-05-01, updated 2026-10-07). Checked 2026-10-17.
- Publish the agent at least once, then agent top menu **Channels** -> **Teams and Microsoft Copilot** tile -> **Add channel** (keep **Make agent available in Microsoft Copilot** selected for M365 Copilot). SCREENSHOT: copilot_channels_teams — Channels page with Teams and Microsoft Copilot tile and Add channel.
- **Teams + Microsoft 365 channels only support "Authenticate with Microsoft"**; other agent-level auth options block those channels. (This is agent-level user auth under Settings -> Security -> Authentication, separate from the MCP tool's OAuth to Canvas.) SCREENSHOT: copilot_agent_auth_settings — Settings > Security > Authentication with Authenticate with Microsoft.
- Distribution: **See agent in Teams** -> **Add**; **Availability options** -> **Copy link**; **Show to my teammates and shared users** (Built with Power Platform); or **Show to everyone in my org** -> **Submit for admin approval** (Teams admin center -> Manage apps, section "Built for your org" / M365 Agent Store "Built by your org"). Org must allow Power Platform apps in Teams admin center. Sharing must be configured before others can install.
- Group/channel chats: agents can't use knowledge sources requiring end-user auth in group chats; this page says nothing about MCP tools requiring per-user sign-in in group chats. Not documented; ask Microsoft.
- Known unsupported in Microsoft Copilot channel: see page list (no Conversation Start topic, etc.).
- Whether MCP tool sign-in works inside Teams / M365 Copilot (connection consent card behavior): the page does not document it. Not documented; verify in a test tenant.

### A5. Limitations / unknowns

- Static client: supported via Manual. Authorization URL, Token URL template, Refresh URL, Client ID, Client secret, Scopes all editable. Labels: "Token URL template", not "Token URL".
- Dynamic client registration not needed.
- PKCE: not documented. Not documented whether Copilot Studio uses PKCE with Manual; ask Microsoft.
- Token endpoint auth method (body vs basic): not documented.
- Accept-header workaround in the repo: not documented anywhere I could read. A search for the 406/Accept-header issue found nothing.

### B1. Facts from readable sources

- superhuman.com/go: "Connect to the apps you use most through pre-built or custom MCP connectors." Anyone on Pro, Business, or Enterprise can build custom agents (agents, not connectors). No OAuth, admin, or redirect info on the page. Connector store: https://superhuman.com/store/connectors.
- Custom MCP connectors are built as Packs (Coda Packs SDK) by a developer: `pack.addMCPServer({name, endpointUrl})`, one MCP server per connector, Streamable HTTP endpoint required, domain declared via `addNetworkDomain()`. Builder needs Doc Maker access in their Docs workspace; user needs Pro or higher to install/use. Users find them via Go side panel -> **Connectors** (lower-left).
- Auth: `setUserAuthentication({type: OAuth2, ...})`. With `useDynamicClientRegistration: true`, no client ID/secret/URLs are set. Servers without DCR: write `authorizationUrl`, `tokenUrl`, `scopes`, `useProofKeyForCodeExchange` in code, register your own app with the provider, and "upload the client credentials on the Settings screen of Pack Studio." (Pack Studio's Generate dialog has "OAuth (Manual)".)
- Redirect URI: Not documented on the pages read. The repo comment says the Canvas LMS Pack's coda.io redirect URI must not be reused; consistent. Obtain the real URI from Pack Studio's settings or Superhuman.
- Each tool is treated as an action needing confirmation unless the server sets `readOnlyHint`.
- Testing: `packs execute` doesn't support MCP/DCR; test by uploading to Go.
- Admin: search snippet of the help center (not read) says admins use the Go settings page to open Go to "Entire organization" or specific member groups, control whether users can build their own agents, and whether users can request access to connectors and agents. Unverified because the article was 403.

### B2. Verdict on custom MCP connector with static OAuth credentials

- Supported in principle through the Packs SDK route (developer-built connector, manual OAuth with uploaded Client ID/secret in Pack Studio Settings). This is a developer workflow in Coda/Superhuman Docs, not a documented in-Go "paste an MCP URL + client ID/secret" form.
- A direct Go UI for adding a custom MCP server by URL with client ID/secret: Not documented (in readable sources).
- Personal vs workspace/admin flow for a custom connector: Not documented in readable sources. The snippet suggests admins govern access and "request access" for connectors; unverified.
- Ordered UI steps with labels: cannot be produced from verified sources. Developer-flow outline only (no screenshots marked as verified):
  1. Doc Maker creates a Pack in Pack Studio. SCREENSHOT: packstudio_new_pack — new Pack with MCP server code. (Label not verified.)
  2. Code: addMCPServer + OAuth2 manual (authorizationUrl, tokenUrl, scopes, PKCE).
  3. Pack Studio -> Settings -> upload Client ID and secret. SCREENSHOT: packstudio_settings_oauth_credentials — Settings screen with client credentials. (Exact labels unverified.)
  4. Copy the redirect URI shown by Pack Studio into the Canvas key. Not documented where it appears.
  5. Upload/release; in Go side panel -> **Connectors**, install; sign in to Canvas. SCREENSHOT: go_connectors_panel — Go side panel Connectors list.
